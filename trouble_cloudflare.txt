ROOT CAUSE / LESSON
-------------------
There are two separate failure classes:

A. Dependency resolver instability.
   Manually invented/unpublished MUI patch versions caused Bun resolution failures. Exact internal MUI package pins are unsafe.

B. CRA/Webpack + MUI export-shape failure in the newer MUI packages tested during this cycle.
   Multiple MUI v5 versions reached production compilation and failed on utility export analysis. Chasing utility names or editing `node_modules` only moved the failure to another utility.

The correct preventive response is to return to the earlier known-good application dependency baseline and avoid modifying vendor packages during the build. The frontend build should use a stable, published MUI baseline and a stable Node version, while the trading architecture remains untouched.

STRICT PREVENTION RULES
-----------------------
- Do NOT patch or rewrite files inside `node_modules/@mui`.
- Do NOT create regex-based source rewrites for MUI utility imports.
- Do NOT change MUI versions one patch at a time in response to the next missing export.
- Do NOT force internal MUI packages such as `@mui/utils`, `@mui/system`, `@mui/styled-engine`, or `@mui/private-theming` to an arbitrary exact version.
- Do NOT run a second package manager during the Cloudflare build.
- Do NOT run `npm install` after Cloudflare has already run `bun install`.
- Do NOT run `npm audit fix --force` during deployment troubleshooting.
- Do NOT change trading architecture to fix a frontend dependency error.
- If a dependency change is required, verify that the exact published version exists before committing it.
- Prefer the historical known-good baseline over speculative upgrades.
- Keep Node 20 for the CRA 5 build unless a deliberate migration away from CRA is performed.
