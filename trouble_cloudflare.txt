CLOUDFLARE DEPLOYMENT TROUBLE RECORD
====================================

Purpose
-------
This file records a recurring Cloudflare deployment regression. The same class of problem has happened multiple times. Do not repeat the same troubleshooting cycle by changing working architecture or dependencies without evidence.

Observed Cloudflare environment
-------------------------------
- Workers Builds detects Bun 1.2.15 and Node.js 24.18.0.
- Cloudflare automatically runs `bun install` before the configured build command.
- The historical configured build command is `npm install --legacy-peer-deps && npm run build`.
- That creates two dependency-resolution phases: Bun first, then npm.

Incident timeline
-----------------
1. The frontend previously built successfully under the established Cloudflare architecture.
2. MUI packages were then changed repeatedly while troubleshooting deployment/build behavior.
3. Attempts included 5.18.0, 5.17.1, 5.15.14 and 5.14.20.
4. 5.18.0 failed before compilation because Cloudflare/Bun reported no matching versions for `@mui/utils@5.18.0` and `@mui/private-theming@5.18.0`.
5. 5.14.20 failed dependency resolution for `@mui/icons-material@5.14.20`.
6. 5.15.14 installed, but the npm production build failed with:
   Attempted import error: 'elementAcceptingRef' is not exported from '@mui/utils'.
7. The 5.16.14 attempt installed successfully through Bun, but the subsequent npm build failed with:
   Attempted import error: '@mui/utils/chainPropTypes' does not contain a default export (imported as 'chainPropTypes').

Root cause pattern
------------------
The repeated failure is caused by an incoherent dependency graph during the second npm installation. `@mui/material` is pinned to 5.16.14, but npm can satisfy its transitive `@mui/*` ranges with a newer MUI v5 internal package. That produces a package family mismatch at compile time. The Cloudflare log is especially important because Bun successfully installed the requested public packages before npm was invoked.

Corrective strategy
-------------------
- Keep only the public application-level MUI packages directly declared: `@mui/material` and `@mui/icons-material`.
- Pin those two packages to the same verified MUI v5 release available to the Cloudflare/Bun resolver: 5.16.14.
- Do NOT directly import or normally declare MUI internal implementation packages at application root.
- Add a defensive `overrides` policy for the MUI internal packages that `@mui/material` depends on: `@mui/core-downloads-tracker`, `@mui/private-theming`, `@mui/styled-engine`, `@mui/system`, and `@mui/utils`, all pinned to 5.16.14. This prevents the historical npm second-install phase from silently upgrading only part of the MUI family.
- Prefer one package manager for the actual build. The repository exposes `build:cloudflare` as `bun run build` and the Cloudflare dashboard should use that command.
- Do not add a prebuild dependency reinstallation step.

Why 5.18.0 is NOT the baseline
-------------------------------
The 2026-08-31 Cloudflare logs explicitly report no matching `5.18.0` versions for `@mui/utils` and `@mui/private-theming` in the target resolver. Therefore 5.18.0 must not be forced across the internal MUI family.

Why 5.14.20 is NOT the baseline
--------------------------------
The Cloudflare log explicitly reported no matching `@mui/icons-material@5.14.20`. Do not restore 5.14.20 merely because it is numerically older.

Current package policy
----------------------
- `@mui/material`: 5.16.14
- `@mui/icons-material`: 5.16.14
- MUI internal packages are not direct application dependencies.
- MUI internal packages are defensively constrained by `overrides` at 5.16.14 so npm cannot create a mixed MUI v5 graph.
- No `npm audit fix --force` during deployment troubleshooting.

Cloudflare build configuration
------------------------------
Preferred Workers Builds configuration:
- Root directory: `fronted`
- Build command: `bun run build`
- Deploy command remains the existing Python Workers deployment command.

If the Cloudflare dashboard still uses `npm install --legacy-peer-deps && npm run build`, change it to `bun run build`. The repository's overrides are an additional safety net, not a reason to keep the two-package-manager build path.
