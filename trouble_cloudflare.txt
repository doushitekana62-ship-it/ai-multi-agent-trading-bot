CLOUDFLARE DEPLOYMENT TROUBLE RECORD
====================================

Purpose
-------
This file records a recurring Cloudflare deployment regression. The same class of problem has happened multiple times. Do not repeat the same troubleshooting cycle by changing working architecture or dependencies without evidence.

Observed Cloudflare environment
-------------------------------
- Workers Builds detects Bun 1.2.15 and Node.js 24.18.0.
- Cloudflare automatically runs `bun install` before the configured build command.
- The historical configured build command was `npm install --legacy-peer-deps && npm run build`.
- That created two dependency-resolution phases: Bun first, then npm.

Incident timeline
-----------------
1. The frontend previously built successfully under the established Cloudflare architecture.
2. MUI packages were then changed repeatedly while troubleshooting unrelated deployment/build behavior.
3. Attempts included 5.18.0, 5.17.1, 5.15.14 and 5.14.20.
4. 5.18.0 failed before compilation because Cloudflare/Bun reported no matching versions for `@mui/utils@5.18.0` and `@mui/private-theming@5.18.0`.
5. 5.14.20 also failed dependency resolution for `@mui/icons-material@5.14.20`.
6. 5.15.14 installed, but the npm production build then failed with:
   Attempted import error: 'elementAcceptingRef' is not exported from '@mui/utils'.
7. Earlier 5.17.1/5.18.0 attempts also produced MUI internal export failures.

Root cause pattern
------------------
The recurring failure is not solved by selecting an arbitrary older MUI number. The project was directly pinning MUI internal implementation packages (`@mui/utils`, `@mui/system`, `@mui/private-theming`, `@mui/styled-engine`, `@mui/core-downloads-tracker`) and repeatedly forcing their versions. This made the dependency graph fragile and exposed the build to registry/version availability differences in Cloudflare's Bun environment.

Corrective strategy
-------------------
- Do NOT directly pin MUI internal implementation packages unless the application imports them directly.
- Keep only the public application-level MUI packages directly declared: `@mui/material` and `@mui/icons-material`.
- Pin those two packages to the same verified MUI v5 release that is available to the Cloudflare/Bun resolver: 5.16.14.
- Let `@mui/material` resolve its compatible internal dependencies transitively rather than overriding them at the application root.
- Do not use an `overrides` block to force internal MUI versions.
- Do not add a `prebuild` dependency reinstallation step; Cloudflare already performs `bun install` before the build and a second resolver only increases risk.
- Prefer one package manager for dependency resolution and build.

Why 5.18.0 is NOT the baseline
-------------------------------
The 2026-08-31 Cloudflare log explicitly reports:
- No version matching `5.18.0` for `@mui/utils`.
- No version matching `5.18.0` for `@mui/private-theming`.
Therefore 5.18.0 must not be forced across the internal MUI family merely because another MUI package has that release.

Why 5.14.20 is NOT the baseline
--------------------------------
The Cloudflare log explicitly reported no matching `@mui/icons-material@5.14.20`. Do not restore 5.14.20 merely because it was previously considered a baseline.

Current package policy
----------------------
- `@mui/material`: 5.16.14
- `@mui/icons-material`: 5.16.14
- No direct root pins for MUI internal packages.
- No MUI overrides.
- No npm `--legacy-peer-deps` dependency installation in the repository build script.

Cloudflare build configuration
------------------------------
Preferred Workers Builds configuration:
- Root directory: `fronted`
- Build command: `bun run build`
- Deploy command remains the existing Python Workers deployment command.

If the Cloudflare dashboard still uses `npm install --legacy-peer-deps && npm run build`, change it to `bun run build` so dependency resolution is not performed twice.

Architecture protection rules
-----------------------------
- Do not reintroduce an AI_ENGINE Cloudflare service binding.
- Do not move the CPython multi-agent Orchestrator into the Cloudflare Python Worker merely to simplify deployment.
- Do not replace real INDODAX market data with synthetic browser samples.
- Do not remove Durable Object manual ON/OFF paper-trading control.
- STOP must remain authoritative and must prevent future paper cycles.
- Real exchange execution remains locked during this development/reconnect phase.
- Do not add real exchange credentials during deployment troubleshooting.

Market Pulse requirement that must not be lost
----------------------------------------------
- Source remains real public INDODAX trades.
- Rolling window remains 30 minutes.
- One segment represents one minute.
- Any actual price change occurring inside a minute must be represented; it must not depend only on browser polling samples.
- No trade data for a minute is FLAT/GRAY.
- The market data must remain usable by the trading analysis/AI pipeline.

Dependency protection rules
---------------------------
- Verify package existence in the actual target resolver before pinning a version.
- Do not force versions of MUI internal packages that the application does not import directly.
- Do not mix Bun installation and npm installation in the production build path when avoidable.
- Do not run `npm audit fix --force` during deployment troubleshooting.
- Do not change application architecture to solve a frontend dependency-resolution error.
