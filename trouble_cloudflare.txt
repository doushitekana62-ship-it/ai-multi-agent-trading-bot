INCIDENTS RECORDED
------------------
1. MUI 5.18.0 dependency-resolution failure.
   Cloudflare/Bun reported no matching versions for:
   - `@mui/utils@5.18.0`
   - `@mui/private-theming@5.18.0`

2. MUI 5.14.20 dependency-resolution failure.
   Cloudflare/Bun reported no matching version for:
   - `@mui/icons-material@5.14.20`

3. MUI 5.15.14 production compilation failure.
   Cloudflare installed the family, then React compilation failed with:
   `Attempted import error: 'elementAcceptingRef' is not exported from '@mui/utils'.`

4. MUI 5.16.14 production compilation failure.
   Bun installed all seven MUI packages at 5.16.14 and the preflight passed.
   React compilation failed with:
   `Attempted import error: '@mui/utils/chainPropTypes' does not contain a default export (imported as 'chainPropTypes').`
   This reproduced with the Bun-only build path, so it was not explained only by a second npm installation.

5. MUI 5.16.6 production compilation failure — 2026-08-31 04:24.
   Cloudflare/Bun installed the complete 5.16.6 family and the preflight passed.
   React compilation failed with the same `chainPropTypes` default-export error.

6. MUI 5.15.6 production compilation failure — 2026-08-31 04:27.
   Cloudflare/Bun successfully installed:
   - `@mui/material@5.15.6`
   - `@mui/icons-material@5.15.6`
   The preflight passed:
   `[CLOUDFLARE-DEPS] MUI family verified: all 7 packages are 5.15.6.`
   React compilation then failed with:
   `Attempted import error: 'elementAcceptingRef' is not exported from '@mui/utils' (imported as 'elementAcceptingRef').`
   Therefore changing only the MUI version is NOT sufficient. The failure is at the MUI utility import/export boundary consumed by CRA/Webpack.

ROOT-CAUSE UPDATE
-----------------
The evidence now supports two separate failure classes:

A. Resolver availability.
   Cloudflare/Bun rejected the tested 5.18.0 and 5.14.20 package versions before compilation.

B. React production-build compatibility.
   Multiple internally consistent MUI v5 families installed successfully, passed the version preflight, and still failed when CRA/Webpack processed MUI utility exports.

Therefore this must no longer be treated as a simple MUI version mismatch. The failing boundary is the way the installed MUI packages import `elementAcceptingRef` and `chainPropTypes` from `@mui/utils` during the CRA/Webpack production build.

CURRENT CORRECTIVE STRATEGY — 2026-08-31
-----------------------------------------
1. Return to the historically used/resolvable MUI 5.17.1 family:
   - `@mui/material`: 5.17.1
   - `@mui/icons-material`: 5.17.1
   - `@mui/core-downloads-tracker`: 5.17.1
   - `@mui/private-theming`: 5.17.1
   - `@mui/styled-engine`: 5.17.1
   - `@mui/system`: 5.17.1
   - `@mui/utils`: 5.17.1

2. Keep the Cloudflare build path single-manager:
   Cloudflare `bun install` -> `bun run build`.
   Do not run a second `npm install`.

3. Add a deterministic prebuild compatibility patch.
   `fronted/scripts/patch-mui-webpack-compat.js` scans installed MUI JavaScript and rewrites root `@mui/utils` imports of `elementAcceptingRef` and `chainPropTypes` to their direct utility subpaths. This targets the exact export boundary implicated by the compiler errors instead of changing application architecture.

4. The dependency validator runs after the patch and fails closed if:
   - any of the seven MUI packages is not exactly 5.17.1, or
   - any forbidden root utility import remains.

5. No second package manager is allowed during the Cloudflare build.

WHY THIS CHANGE
---------------
The 04:27 build disproved the assumption that another MUI rollback would solve the problem. We therefore return to the historical 5.17.1 application baseline and patch only the build-time compatibility boundary implicated by the actual compiler error.

This is a targeted frontend build compatibility fix. It does not alter the trading architecture, Market Pulse behavior, paper-trading controls, or AI-agent design.
